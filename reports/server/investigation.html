F# Compiler Server: making it faster

Per-compilation and whole-build experiments on the compiler server branch (repos/server), 2026-10-18, 11-core Apple M-series. Plan: plan.html · first results: results.html · code: compiler_server (diff).

Summary

  • Your result reproduces. Per compilation, a warm worker is much faster than stock fsc + JIT flags, in both wall time and CPU. Summed over 5 projects, the wall time falls by 25–30% and CPU by 35–45%. Small and medium projects take 0.2–0.6× of the flags' time; FCS takes 0.85–0.9×.
  • Whole builds needed the workers tuned. The first version was only level with the flags on whole builds. Two one-line worker settings fixed that, and both are now the branch default:
    • DOTNET_TC_CallCountingDelayMs=0, keeping Tiered PGO on. A new worker used to compile its first large project at stock speed (FCS 26–28 s, against 14 s with the flags). Now it tiers up as fast as a JIT-flagged process, and steady state is unchanged.
    • Non-concurrent GC: about 13% less CPU per compilation and 12% faster FCS-solution builds.
  • Whole builds with the new defaults:
    • Fantomas: 19.4 s, against 25.3 s for stock + flags (−23%) and 30.2 s for stock (−36%). CPU −44%. It repeats to within about 0.3 s.
    • FSharp.Compiler.Service.slnx: 39.0 s mean over 8 builds (36.3–41.4 s), against 45.7 s (−15%), CPU about −35%. This solution is dominated by the FCS compilation, where the JIT is only 2–3% of CPU and GC is 31–39%.
  • Not worth it:
    • Reusing assembly caches between compilations: a warm worker's imports already take about 0.05 s.
    • Tiered PGO off in workers: 11% slower at steady state.
    • All cores as GC heaps per worker: 28% slower than the flags on parallel builds (47% slower than 5 heaps), as you expected.
    • Skipping the idle-time GC: no effect.
  • Outputs: every server compilation and build produced the same assemblies as stock (main and reference assemblies, compared by hash).
  • Occasional slow builds: explained as MSBuild scheduling.
    • About 4 of 40 warm FCS-solution server builds took 53–55 s instead of about 37–45 s; none of the 12 stock / stock + flags builds did.
    • The per-compilation timing now in the build log caught one. FCS's two target frameworks were built one after the other on the same MSBuild node: the netstandard2.0 compilation started 23 s after net11.0, instead of together. Everything that depends on FCS then waited.
    • The compilations themselves were faster than usual (11.9 and 11.3 s, against about 15.5 s when they overlap), and the client added at most 0.05 s per compilation.
    • Whether the server makes this ordering more likely is not established.

Where the time goes in a large compilation (FCS)

Native sampling with macOS sample (1 ms, every thread), self samples of busy threads grouped by what runs: managed compiler code (JIT'd or ReadyToRun, unsymbolized), GC (gc_heap functions in libcoreclr), JIT (libclrjit), other runtime code, other native code. Sampling slows the compilation, so read shares, not times.

Whole builds

dotnet build -c Release --no-restore --no-incremental, MSBuild node reuse off, 1 warm-up and 3 measured builds per config, configs run one after another. Server configs include worker affinity; their worker settings go to the workers only (FSHARP_COMPILER_SERVER_WORKER_*). CPU = build process tree + live workers.

Not done yet, worth trying next

  • Slow-build ordering: the occasional slow builds come from MSBuild running FCS's two target frameworks one after the other. Next: more stock builds to see whether it happens there too at a lower rate, and whether -graph builds avoid it.
  • Pre-warm new workers: start one spare worker ahead of need, or let a new worker compile a small embedded sample before its first request. Fast tier-up already removed most of the cold cost, so this is worth it only if cold builds still matter.
  • Allocation profile of FCS (33 GB per compilation): the largest remaining cost for big projects, with or without the server.
  • Linux x64 with many cores (your work setup): the heap count and the non-concurrent GC choice should be checked there, where more compilations run at once.
  • Ship: dotnet build-server shutdown integration (dotnet/sdk), a version handshake and worker logging.
